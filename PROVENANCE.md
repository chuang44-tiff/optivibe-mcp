# PROVENANCE.md — data provenance and license ledger

OptiVibe ships **code only**. No vendor data files — no glass catalog data, no
manual text, no operand descriptions derived from vendor documentation — are
committed to this repository. Everything the reference layer grounds on is
**built locally, on your machine, from your own licensed Zemax OpticStudio
install**, and the build outputs are fenced out of git (see the `.gitignore`
files at the repo root and in `packages/optivibe-reference/`).

## How the local build works

Run after installing (see the install guide):

    python packages/optivibe-reference/scripts/build_vendor_data.py

That orchestrates the local build:

- `build_glass_catalog.py` — reads the `.agf` glass catalog files from your
  install's Glasscat directory (`ZEMAX_GLASSCAT` env override, else
  `~/Documents/Zemax/Glasscat`), re-parses and recomputes every record with
  OptiVibe's own parser + dispersion engine, and writes
  `data/glass_catalog.json` (gitignored). No raw `.agf` content is retained —
  the files are read at build time and discarded.
- `build_manual_corpus.py` — indexes your install's
  `OpticStudio_UserManual_en.pdf` (`OPTIVIBE_MANUAL_PDF` env override, else the
  standard install dir) into a local SQLite FTS5 database
  `data/manual_corpus.db` (gitignored) plus a text-free
  `data/manual_manifest.json` (gitignored). Run with `--emit-raw` it also writes
  the gitignored **verbatim raw operand/tolerance description extracts** used by
  the next two steps. If the PDF is absent (no licensed install on this machine)
  the step skips cleanly; the server degrades the manual-search tool with a
  typed `corpus_unavailable` answer.
- **merit + tolerance operand catalogs** (`catalog_build.py` /
  `tolerance_build.py`) — merge the **committed** synonyms sources
  (`operand_synonyms.json`, `tolerance_operand_synonyms.json` — OptiVibe's own
  intent-mapping judgment, not vendor data) with your install's live-probe
  captures (generated by `scripts/probe_operands.py` + `scripts/probe_tolerances.py`,
  which boot a headless engine, read the `MeritOperandType` / `ToleranceOperandType`
  enum surface, and write gitignored captures under `scripts/captures/` — run them
  once first) and, when present, the verbatim-local manual description extract, into
  `data/operand_catalog.json` / `data/tolerance_operand_catalog.json`
  (gitignored). Because those catalogs embed **verbatim manual descriptions**,
  they are built locally and **never committed** — the same license basis as the
  FTS5 corpus. Absent the live-probe captures the step skips cleanly and the
  operand tools degrade with a typed `operand_catalog_unavailable` answer; absent
  the manual extract the catalog builds **synonyms-only** (every description
  marked pending). The committed synonyms + `operand_semantics.json` sources are
  authored by OptiVibe and ship in the repo; only the description-bearing
  catalogs are user-built.

Both builders **fail closed** unless the corresponding grant row below is on
file in this ledger. This guards against a fork silently widening what may be
derived.

## The commit fence

The built artifacts are for the licensed user's own local use and must never be
committed or redistributed. The `.gitignore` fence covers `*.db`, the built
data JSONs (`glass_catalog.json`, `manual_manifest.json`, the description-bearing
`operand_catalog.json` / `tolerance_operand_catalog.json`, and any local
`*_descriptions.json`), and `scripts/captures/` (the live-probe captures + the
verbatim raw description oracles). If you fork this repository, keep the fence
intact: committing your locally built data would redistribute material derived
from your vendor license. The committed sources — the `*_synonyms.json` and
`operand_semantics.json` files (OptiVibe's own authored intent/semantics layer) —
carry no vendor prose and are the only reference-data files in the repo.

## No vendor SDK files

No vendor SDK files are vendored into this repository. OptiVibe drives
